# ArenaMind AI

**A GenAI-powered stadium companion for the FIFA World Cup 2026 Smart Stadiums & Tournament Operations Hackathon.**

ArenaMind AI is a live, conversational assistant that helps a fan complete an entire stadium visit — finding their seat, ordering food, getting emergency help, translating a phrase, checking transport, tracking a lost item, or getting match info — through one chat interface, with every answer grounded in the venue's own data and only its *phrasing* generated by an LLM.

## Chosen Vertical

**Persona: Fans.** A first-time visitor to an unfamiliar mega-stadium during the FIFA World Cup 2026 faces a fragmented experience — a paper map for navigation, a separate app for food, a volunteer to flag down for an emergency, no one who speaks their language, and no idea which exit or transit option is fastest after the final whistle. ArenaMind AI replaces all of that with a single conversation that understands *who this fan is right now* — their stadium, their linked seat, their language, their accessibility needs — and never makes them repeat information they've already given.

We deliberately did **not** build organizer dashboards or volunteer/staff tooling in this submission — the fan-facing experience is the product, kept sharp and complete rather than spread thin across personas.

## Approach & Logic

The core design decision behind ArenaMind AI is a strict separation between **deciding facts** and **phrasing language**:

```
User → Intent Engine → Orchestrator → Agent → Tool → Knowledge Base
     → Structured Verified Facts → Grounded Response Generation → Response
```

- **Every fact is computed deterministically.** Which gate is closest, which vendor has the shortest queue, which exit to take, which medical team to dispatch — all of this comes from plain TypeScript logic reading a local JSON knowledge base (`src/knowledge`). An LLM is *never* in the decision path for these.
- **An LLM only rephrases an already-correct answer into natural language**, streamed token-by-token from [Groq](https://groq.com). It's given the deterministic answer plus the raw tool data behind it, and is explicitly instructed to never add, remove, or change a fact, a number, or a name — only to explain *why* a recommendation was made, in the fan's own language, referencing what's already known about them (seat, stadium, accessibility needs, recent conversation).
- **Emergency responses are 100% template-driven**, with no LLM call at all — safety-critical facts (nearest medical team, exit, ETA) must never pass through a model that could alter them.
- **Every LLM call degrades gracefully.** If Groq is slow, times out, or its quota is exhausted, the assistant falls back to the deterministic template reply instead of ever going silent or crashing. This was verified live, not assumed — see [Known Limitations](#known-limitations).

This split is what makes the assistant genuinely GenAI-powered (natural, non-repetitive, explains its own reasoning) *without* opening the door to hallucinated stadium facts, which is the one failure mode that's unacceptable in a safety-adjacent, real-time venue assistant.

## How It Works

1. **Intent Engine** (`src/ai/intent-engine.ts`) classifies the fan's message using Groq with structured output, falling back to a keyword classifier if the model is unavailable. A hard safety override always routes a real emergency signal (e.g. "fire", "collapsed") to the Emergency agent, regardless of what either classifier decides.
2. **Context & Memory Engines** (`src/ai/context-engine.ts`, `src/ai/memory-engine.ts`) resolve who's asking — stadium, language, linked seat, accessibility preferences, and recent conversation — so the assistant never re-asks for information it already has (e.g. "Someone fainted" correctly recalls a seat linked three turns earlier).
3. **Agent Router** (`src/ai/orchestrator.ts`) dispatches to one domain agent per intent — Navigation, Food, Emergency, Translation, Venue, Transport, Match, Lost & Found — each of which calls one or more **Tools** (`src/tools`) that read the **Knowledge Base** (`src/knowledge`) and return a deterministic, already-correct answer.
4. **Grounded Response Generation** (`src/ai/response-generator.ts`) takes that answer plus its raw supporting data and streams a natural-language rewrite from Groq — the only place an LLM touches the final reply, and only to rephrase, never to decide.
5. The reply streams to the browser over a lightweight NDJSON protocol as real tokens arrive, rendered with a live typing cursor in the chat UI.

**Example conversation:**

```
Fan:  My seat is Section 102, Row F, Seat 18
Bot:  Section 102 — Row F, Seat 18 is closest to Gate B. Estimated walking time: 4 minutes.

Fan:  I'm hungry, what's nearby?
Bot:  Green Bowl Kitchen is your best bet — about 5 min wait at Block C, Level 1.
      Recommended because it currently has the shortest queue and low crowd levels.

Fan:  Someone fainted near me
Bot:  Medical help is being notified. You're at Section 102 — Row F, Seat 18.
      Nearest help: Medical Center North, about 3 min away. Stay where you are
      if it's safe to do so. [no seat re-ask — already known from turn 1]
```

## Tech Stack

- **Next.js 15** (App Router) + **React 19** + **TypeScript**
- **Groq** (`openai/gpt-oss-120b`) via the **Vercel AI SDK** (`ai`, `@ai-sdk/groq`) for intent classification, grounded response generation, and translation — real token streaming, no fake typing simulation
- **Tailwind CSS 4** + shadcn-style UI primitives, **Framer Motion** for animation
- **Jotai** for client state, **Three.js / React Three Fiber** for a small 3D accent layer
- A local JSON **knowledge base** (`src/knowledge`) as the sole source of stadium facts — no external APIs, no database

## Getting Started

1. Install dependencies:
   ```bash
   npm install
   ```
2. Add a Groq API key (free at [console.groq.com](https://console.groq.com) → API Keys) to `.env.local`:
   ```
   GROQ_API_KEY=gsk_...
   ```
3. Run the dev server:
   ```bash
   npm run dev
   ```
4. Open [http://localhost:3000](http://localhost:3000) and go to **Assistant** to chat, or **Profile** to switch stadium/language/accessibility settings first.

> **No Groq key, or hit a quota limit?** The assistant still works — every reply falls back to a deterministic, grounded template instead of failing. See [Known Limitations](#known-limitations).

## Assumptions Made

- **Demo data, honestly labeled.** Vendor queues, crowd levels, and walking times are illustrative demo data (`src/knowledge`), not a live IoT/POS feed — replies say "(demo data)" where relevant rather than implying real-time sensors.
- **One active stadium at a time**, chosen from three configured venues (MetLife, Hard Rock, Estadio Azteca) via Profile — not a live multi-venue directory.
- **Session-scoped memory, not persistent accounts.** Conversation memory lives in server process memory for the active session; there's no login, no database, no cross-device sync in this MVP (documented in `docs/AI-Architecture/02-AI-Architecture.md`).
- **Intent understanding is English-only.** The assistant's *output* is generated in the fan's preferred language (English/Spanish/French), but the intent classifier currently reads English input.
- **Food ordering and lost-item reports are simulated** — no real payment, no real physical lost-and-found integration; both are clearly framed as such in the replies.
- **A shared Groq free-tier API key has a daily token quota.** Heavy use (including our own adversarial QA pass) can exhaust it; the assistant is designed to degrade gracefully rather than break when that happens — see below.

## Accessibility

- Full keyboard navigation, including a keyboard-only send flow (focus → type → Enter, no mouse required)
- Proper ARIA roles and landmarks (including on the interactive stadium map SVG), a real `<h1>` on every route, and no duplicate tab stops
- All interactive touch targets meet the 48×48px minimum (one disclosed, deliberate exception: small map pins, matching standard map/diagram UI conventions)
- `prefers-reduced-motion` respected on animated flows
- Wheelchair/accessibility preferences set in Profile automatically bias navigation and facility recommendations toward accessible routes — the assistant never asks the fan to repeat this preference

## Testing & QA

This project was verified by actually running the app end-to-end — live requests against the real streaming endpoint and a real browser (Playwright) — not by reading code and assuming behavior. Two rounds are documented in full:

- [`RC1-RELEASE-REPORT.md`](RC1-RELEASE-REPORT.md) — full-app QA pass (navigation, accessibility, responsive layout, error handling).
- [`GENAI-INTEGRATION-REPORT.md`](GENAI-INTEGRATION-REPORT.md) — the GenAI integration itself, including an adversarial QA pass that deliberately tried to break memory, hallucinate facts, misroute intents, break streaming, and find dead buttons — with every real bug found, root-caused, fixed, and re-verified live.

`tsc --noEmit`, `eslint`, and `next build` all run clean.

## Known Limitations

- **Groq's daily token quota is shared and finite.** Our own testing exhausted it mid-development; when that happens the assistant automatically falls back to deterministic template replies (verified — see `GENAI-INTEGRATION-REPORT.md` §7) rather than erroring, but loses the natural, varied phrasing until quota recovers. For a fresh demo, use a Groq key with unused quota.
- Intent classification is occasionally non-deterministic between identical repeated messages (inherent to LLM-based classification); every path it can land on has been verified to degrade safely rather than hallucinate.
- No automated test suite — verification is manual, live-request based, consistent with how this project has been QA'd throughout.
